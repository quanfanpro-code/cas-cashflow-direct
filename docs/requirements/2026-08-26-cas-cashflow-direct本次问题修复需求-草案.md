# cas-cashflow-direct 东方农博运行问题修复需求

日期：2026-08-26

状态：用户已批准实施。需求优先工作流检查点1、检查点2均通过；完成验收后提交、推送，并同步README等文档。

## 背景、用户与目标

1. 本轮问题来自`东方农博2025.xlsx`的直接法现金流量表真实运行。使用者需要在Excel内完成人工复核、形成正表并核对现金余额变动。
2. 当前结果存在七个共同问题：人工表把多个金额拼入一个单元格；低金额系统兜底结果缺少独立抽查和人工改选工作表；未决金额在现金勾稽中丢失；直接存货入口路径被重复采购标志错误拦截并显示为0分；真实现金业务可以仅凭“无法分类”等自由文字被人工排除；同一凭证混有真实付款和非现金计提时，业务组成错误合并并把明确工资业务转入人工；人工表为同一业务额外生成不存在于原始资料的“批次主行”，造成字段空白、真实明细重复和内部控制文字暴露。
3. 本轮还增加两项明确要求：原表没有现金流项目且金额低于实际执行重要性时，按两项独立来源的较高分兜底分类，同分优先完整科目路径；“原表与系统决定差异”固定来源1为完整科目路径、来源2为摘要。
4. 目标是修复共同机制，使工作簿可由人工直接操作、金额守恒、未决可追溯、来源顺序稳定，并通过普通回归和本次真实工作簿验收。
5. 重要性边界全部读取每次运行输入，不写入固定金额。本次东方农博最终验收输入为整体重要性25万元、实际执行重要性12.5万元、明显微小错报临界值2.5万元，仅用于本次验收。

## 范围边界

### 本次纳入

1. 人工复核批次、组成明细、金额展示、状态公式和正表联动。
2. 原表现金流项目为空时的低于实际执行重要性兜底分类，以及达到实际执行重要性后的人工出口。
3. 现金变动桥接、未决净额、最终勾稽成功条件和状态文案。
4. 直接存货入口与成本去向路径规则拆分。
5. 差异表两项独立来源的固定顺序。
6. README、SKILL、必要ADR、设计、实施计划、验收报告和更新记录。

### 本次不做

1. 不修改原始客户Excel，不把客户名称、金额、凭证号或行号写入通用生产规则。
2. 不改变已经确认的现金范围、三项重要性金额和自动修改最低证据分。
3. 不增加外部依赖，不建立第二套评分体系，不重写无关模块。
4. 不删除历史文件、接口或用户已有修改。

## 调研与证据边界

1. 根因依据来自本地生产代码、2026年8月24日相关提交历史、本次运行数据库和输出工作簿的只读检查。
2. 本轮不需要外部事实或网络资料；会计处理口径以用户已确认需求和本Skill既有标准项目体系为准。
3. 修复前必须统计直接存货入口额外条件的实际影响，不得把全部人工事项归因于单一规则。

## 一、人工复核事项分表

1. 原方案中的“低金额批量处理”工作表取消，由“低金额系统兜底明细”直接替换，不同时保留两张表。
2. 原表没有现金流量项目且金额低于实际执行重要性的事项，必须由系统兜底形成具体项目，不再设置“低金额人工批量”行动结果。
3. “重要待复核事项”只保留金额达到实际执行重要性后仍未决的事项，以及行动表明确标记为“人工决定”的其他事项。
4. 最终工作簿仍固定为十三张工作表；使用说明、状态判断、正表联动和相关核对必须同步将原“低金额批量处理”替换为“低金额系统兜底明细”。

## 二、低金额系统兜底明细表的真实明细

1. “低金额系统兜底明细”必须直接包含全部真实组成明细，不得生成脱离原始资料的批次主行，也不得要求用户跳转到“全量分类留痕”后才能查看明细。
2. 每条真实明细逐行展示同一业务序号、日期、凭证信息、摘要、完整对方科目路径、现金账户、借方、贷方、现金变化、原现金流项目、系统兜底项目、人工改选项目及最终采用项目等可复核信息。
3. 同一业务的真实明细连续展示；人工只在该业务第一条真实明细选择一次，其他真实明细通过公式同步该选择并显示具体项目名称，不得要求逐条重复选择。
4. 一条明细只能对应一个实际金额；不得在同一金额单元格内使用顿号、逗号或其他文本方式拼接多个金额。
5. 同一业务组成对应多个现金分配金额时，必须展开为多条真实明细。例如一个业务组成对应三笔现金金额时，三笔金额分别占一行，不再额外生成数值合计行。
6. 同一业务金额只通过所属真实明细求和核对，不作为另一条数据行写入，也不得再次计入现金流量表。
7. 每个同一业务序号下的真实明细现金变化合计必须等于该业务应处理金额；不相等时不得生成可使用的最终工作簿。
8. “全量分类留痕”继续保留完整审计轨迹，但不得替代“低金额系统兜底明细”表内应当直接展示的真实明细。

## 三、低金额兜底与重要事项分流口径

1. 原表没有现金流量项目且金额低于实际执行重要性的事项，统一进入系统兜底，不再形成低金额人工批次。
2. 先前拟定的“六项条件相同才组成一批”规则随低金额人工批次一并废止，不再生成低金额批次编号。
3. “重要待复核事项”保留以下事项：原表没有现金流量项目且单笔金额达到实际执行重要性后仍未决的事项；单笔金额达到整体重要性的事项；以及行动表明确要求单独人工决定的其他事项。
4. 系统兜底事项进入“低金额系统兜底明细”，默认结果直接用于正表，同时允许人工抽查和主动改选。
5. 同一业务的真实明细必须连续排列、支持筛选和打印，不得通过折叠或人造主行隐藏真实记录。

### 3.1 无法形成系统候选的事项

1. 现行程序曾把原项目为空、经过规定复核后仍无法形成唯一候选的低金额事项送入“低金额人工批量”，但输出时仍逐项列入“重要待复核事项”，并可能把全部标准项目作为备选；该旧路线本次整体取消，改为系统兜底后集中展示。
2. 本规则适用于原表没有现金流量项目、现金范围已经确认、真实现金金额和方向能够确定、经过正常分类和规定复核后仍无法形成最终项目的事项。摘要或完整路径非法的状态必须继续留痕，但只要真实现金金额和方向已确定，不能据此让低于实际执行重要性的事项继续未决。
3. 单笔金额达到本次运行实际执行重要性的未决事项，进入“重要待复核事项”由人工决定；单笔达到本次运行整体重要性的事项继续按重要事项处理。
4. 单笔金额低于本次运行实际执行重要性时，不允许继续保持未决，必须按两项独立来源兜底确定一个具体现金流量表项目。
5. 兜底时固定比较两项来源：独立来源1为完整对方科目路径来源，独立来源2为摘要来源；采用得分更高的来源。
6. 两项来源同分且指向同一项目时，直接采用该项目。
7. 两项来源同分但指向不同项目时，固定优先采用独立来源1，即完整对方科目路径来源。
8. 两项来源都不能唯一形成项目时，仍不得转人工或保持未决：先按来源得分选择来源，得分相同时优先完整对方科目路径来源，再由被选中的来源结合实际现金方向兜底强判一个具体项目。
9. 兜底决定必须在全量留痕和差异表中记录两项来源各自的分数、候选、被选中的来源、最终项目及“低于实际执行重要性，按较高分独立来源兜底；同分优先完整科目路径来源”的理由。
10. 兜底决定不得伪装成两项来源一致，不得虚增证据分数，也不得删除未被采用来源的原始判断。
11. 低于本次运行实际执行重要性且满足本节适用条件的事项完成兜底后，进入“低金额系统兜底明细”，不再进入任何低金额人工批次或“重要待复核事项”。

## 四、所有人工处理表禁止在一个单元格拼接多个金额

### 4.1 已确认根因

1. 一个业务组成可以对应多条现金分配明细，但现行输出程序要求一个业务组成在人工处理表中只占一行。
2. 输出程序收集该业务组成对应的全部留痕明细；同一字段出现多个不同值时，统一使用顿号拼接。
3. 借方、贷方和流量金额等数值字段错误地复用了文字字段的拼接方式，导致多个金额被写入同一文本单元格。
4. 根本问题是把“业务组成这一分类判断单位”和“现金分配明细这一金额展示单位”混为同一输出粒度。业务组成层本身继续保留；错误发生在人工表的压缩展示方式。
5. 现有测试只检查业务组成的现金变化合计，没有检查借方、贷方和流量金额是否保持单一数值，也没有检查多条现金分配是否逐行展开，因此未能发现该问题。

### 4.2 全局输出要求

1. 本要求适用于“重要待复核事项”“低金额系统兜底明细”及其他所有供人工处理的工作表，不限于低金额事项。
2. 任一金额单元格只能保存一个数值，不得用顿号、逗号、换行或其他文本形式拼接多个金额。
3. 一个业务组成对应多条现金分配时，每条现金分配必须各占一条真实明细行，不得另设人造主行或合计数据行。
4. 日期、凭证号、摘要、完整对方科目路径、现金账户、借方、贷方、流量金额和现金变化必须按对应明细真实展示，不得把多条来源压成一个不可筛选、不可加总的文本值。
5. 同一业务合计只通过公式或校验计算，不写成额外数据行；正表只汇总真实明细金额。

### 4.3 验收条件

1. 人工处理表全部金额列必须保持Excel数值类型，可以直接加总、筛选和排序。
2. 金额列不得出现包含顿号、逗号分隔金额或换行拼接金额的文本单元格。
3. 每个业务组成的校验金额必须等于所属现金分配明细金额合计，且不得为该合计另造数据行。
4. 多现金账户、多来源行和一项业务对应多笔现金金额的测试样例，必须验证各明细逐行展示且正表只计算一次。
5. 测试必须分别覆盖借方、贷方、流量金额、现金变化和单笔金额列，不得只验证业务组成合计。

## 五、未决事项不得在现金勾稽中丢失

### 5.1 核心原则

1. 未决事项可以暂时不进入具体现金流量表项目，但不得从现金勾稽计算中消失。
2. 现金勾稽必须始终满足：

   `已分类现金净额＋尚待分类现金净额＋汇率影响＋已确认且单独披露的调整＝现金范围内账户期末余额－期初余额`

3. 人工确认后，相关金额从“尚待分类现金净额”转入具体现金流量表项目；转移前后现金变动总额必须保持不变。
4. 明确排除的事项必须转入可追溯、单独披露的排除或调整项目；不得通过删除未决金额制造表面相符。
5. 尚待分类现金净额不为零时，只能标记“现金变动桥接相符、现金流量表尚待分类”，不得标记“最终现金流量表勾稽成功”或“最终可使用”。

### 5.2 原表有现金流量项目

1. 原现金流项目有效且金额完整时，未决复核事项继续保留原项目金额作为正表基线，不得因等待复核而从正表中删除。
2. 人工改选后，从原项目转出并转入新项目；项目之间可以变化，但现金净增加额不得变化。
3. 原表明细与现金变动相符，只能说明原表现金明细覆盖完整；存在未完成的必要人工决定时，工作簿仍不得标记“最终可使用”。
4. 原项目为空、无法标准化或原流量金额未覆盖实际现金收付的部分，必须按“原表无现金流量项目”处理。

### 5.3 原表无现金流量项目

1. 已完成分类的金额进入具体现金流量表项目；尚未完成分类的金额全部进入“尚待分类现金净额”。
2. 过程勾稽必须使用“已分类现金净额＋尚待分类现金净额”与现金范围内账户变动比较，不得只用当前不完整的正表净额比较。
3. 过程公式相等时，只能标记“现金变动桥接相符”；尚待分类现金净额归零前，不得称为最终现金流量表勾稽成功。
4. 全部人工决定完成、尚待分类现金净额为零、最终正表净额加汇率影响及已确认调整等于现金余额变动、无法解释差异为零时，才能标记“最终现金流量表勾稽成功”和“最终可使用”。

### 5.4 输出和验收要求

1. 勾稽工作表必须分别列示现金余额变动、已分类现金净额、尚待分类现金净额、汇率影响、已确认调整和无法解释差异。
2. “尚待分类现金净额”必须能够追溯到全部未决业务组成及其现金分配明细。
3. 未决事项新增、完成分类或明确排除时，勾稽桥接自动更新，但现金变动总额始终守恒。
4. 程序不得把尚待分类金额误标为“勾稽差异”；只有完整桥接以后仍不能解释的剩余金额才属于勾稽差异。
5. 测试必须分别覆盖原表项目完整、原表项目全部为空和原表项目部分为空三种输入，并验证未决事项在任何阶段均未丢失。

## 六、直接存货入口路径不得重复要求采购标志

### 6.1 已确认根因

1. 2026年8月24日新增的存货与成本流转语义规则，原设计目的是防止把存货领用、入库、出库、成本结转、主营业务成本归集和制造费用分配等内部流转误判为当期现金采购。
2. 该规则要求存货或成本路径除科目本身外，还必须出现“采购款、材料款、外购商品、物料”等额外标志，才允许形成“购买商品、接受劳务支付的现金”候选。
3. 上述额外条件错误地同时覆盖了两类性质不同的科目：
   - 对生产成本、制造费用、主营业务成本等成本去向科目，要求进一步说明本次支付对象具有合理性；
   - 对材料采购、在途物资、原材料、委托加工物资、周转材料、包装物、低值易耗品等直接存货入口科目，在已经识别真实现金付款时再次要求采购标志，属于重复且错误的限制。
4. `周转材料_低值易耗品`已经属于直接存货入口路径；在借记该路径、贷记已确认现金范围内银行存款且不存在非现金阻断事实时，不应再要求摘要或路径重复出现“采购款”等文字。
5. 现行程序在额外条件未满足时不形成路径候选，随后又把“没有形成候选”的路径结果直接丢弃，最终错误显示为完整路径无效、路径证据0分。

### 6.2 修复要求

1. 存货和成本路径规则必须拆分为“直接存货入口”和“成本去向或内部流转”两类，不得继续共用同一个额外采购标志条件。
2. 直接存货入口路径同时满足以下条件时，可以形成“购买商品、接受劳务支付的现金”路径候选：
   - 已识别真实现金付款；
   - 完整对方科目路径属于直接存货入口；
   - 不存在领用、入库、出库、结转、分配、折旧、摊销、减值等内部非现金阻断事实；
   - 不存在职工、税费、长期资产等优先适用的专用业务属性。
3. 生产成本、制造费用、劳务成本、合同履约成本、主营业务成本及其他成本去向科目，继续要求进一步明确外购材料、商品、加工、外部生产或履约服务、生产用水电燃料等实际支付对象。
4. 领用、入库、出库、完工、成本结转、费用分配等内部流转继续由非现金阻断规则处理，不得因为删除直接存货入口的重复条件而形成现金流候选。
5. “完整路径已识别但被某项条件拦截”必须保留真实识别状态和具体拦截原因，不得含糊显示为“完整路径无效”。

### 6.3 影响统计和验收条件

1. 修复前必须统计本次运行中因该额外采购标志条件未满足而没有形成路径候选的业务数量、金额、原项目状态和最终人工动作；不得把全部726条人工事项笼统归因于本规则。
2. 测试必须覆盖直接现金购买原材料、周转材料、低值易耗品、包装物和委托加工物资，并验证完整路径能够独立形成正确候选。
3. 测试必须覆盖存货采购退款或退回，并验证现金方向及项目方向正确。
4. 测试必须覆盖存货领用、入库、出库、完工、成本结转、主营业务成本归集和制造费用分配，并验证仍被非现金阻断。
5. 测试必须覆盖成本去向科目缺少外购对象和明确外购对象两种情况，验证前者不形成购买候选、后者按完整语义判断。
6. `周转材料_低值易耗品`直接对应真实银行付款且无非现金阻断事实的回归样例，完整路径来源不得再被判为0分。

## 七、“原表与系统决定差异”固定两项独立来源的顺序

1. “原表与系统决定差异”工作表中的“独立来源1”固定为完整对方科目路径来源。
2. “独立来源2”固定为摘要来源。
3. 两项来源不得因分数高低、是否有效、是否形成候选或实际返回顺序而互换位置。
4. 某项来源无效、未形成候选或存在冲突时，仍在其固定来源栏如实展示状态、质量、候选、分数和原因；不得把另一来源移动过来填补。
5. 工作表表头、判断理由、证据质量说明和相关测试必须统一使用上述固定顺序。
6. 测试必须覆盖路径有效摘要无效、路径无效摘要有效、两项均有效以及两项冲突四种情况，并验证来源位置始终不变。

## 八、真实现金业务的排除必须经过受控授权

### 8.1 已确认根因

1. 另一次东方农博2024年运行中，操作者把“系统无法自动分类”错误理解为“该现金业务应当排除”，通过兼容人工决定入口将16个真实现金支出业务组成排除，合计现金变化为-281,363.93元。
2. 直接错误来自操作者违反Skill规则：无法分类不等于没有发生现金收付；兼容人工决定入口也不是普通运行的标准必经步骤；操作者随后直接修改运行状态文件，同样绕过了正常入口和留痕门禁。
3. Skill程序同时存在控制缺陷：兼容人工决定入口允许任何未决业务选择排除，只要求自由文字理由不为空；最终分类校验也只检查排除理由是否为空，没有验证排除是否属于允许情形。
4. 最小构造复现已经确认：一笔真实银行收款因摘要为空进入隔离后，仅填写“无效输入，摘要无法对应现金分类”，程序即可接受人工排除。现有勾稽会产生差异并保持草稿，但没有在排除入口阻止错误决定。

### 8.2 排除授权规则

1. “无法分类”“摘要为空或乱码”“完整路径无效”“证据不足”“候选不唯一”“来源冲突”“低金额”“等待人工”均不是排除依据。
2. 已确认存在真实现金腿的业务，不得通过普通人工决定从现金变动桥接中删除。无法确定具体项目时，必须按本需求的实际执行重要性分流、低金额兜底或重要事项人工决定处理。
3. 只有具有结构化、可验证依据的情形才能排除或作为已确认调整处理，包括：现金范围内账户之间的内部划转、确认为非现金或零金额、经独立重复检查确认的重复业务、经现金范围确认不属于现金及现金等价物的账户，以及用户明确确认且单独披露的调整。
4. 现金范围排除、内部划转和疑似重复事项继续使用各自既有专门入口，不得借普通分类人工决定入口重复排除。
5. 对真实现金腿的用户明确调整，金额不得消失；必须进入“已确认且单独披露的调整”并参与现金变动桥接，记录调整类型、依据、操作者和时间。
6. 兼容人工决定入口收到普通`exclude`请求时，必须同时取得允许的结构化排除类型及对应既有事实；仅有自由文字理由时拒绝执行。
7. 非法输入和低金额人工事项默认不具备排除资格。真实现金金额和方向已经确认且低于实际执行重要性时，即使摘要或路径非法，也由系统保留警告后按已确认来源顺序和现金方向直接形成项目；达到实际执行重要性后仍未决的事项由人工选择具体正表项目。

### 8.3 运行状态完整性

1. 运行状态只能通过正式阶段入口更新；不得通过直接编辑状态文件制造人工决定、清除最终标志或改变运行阶段。
2. 分类决定、人工决定、运行阶段和最终输出之间必须建立可验证的一致性记录。状态文件与留痕数据库不一致时，停止继续运行并提示新建运行或从最后有效阶段恢复。
3. 最终生成前必须重新验证每个排除事项的结构化类型、来源事实、金额去向和桥接归属，不能因为状态字段已经写成`excluded=true`就直接认可。

### 8.4 验收条件

1. 非法输入、证据不足、候选不唯一、来源冲突和低金额事项仅提供自由文字理由时，人工排除请求必须失败。
2. 内部划转、非现金、零金额、已确认重复和现金范围排除继续按专门规则正确处理，不受新增门禁误伤。
3. 用户明确确认的真实现金调整进入单独披露调整，桥接总额保持守恒，不得从已分类净额和尚待分类净额之外消失。
4. 直接修改运行状态中的排除字段、决定项目或运行阶段后，后续阶段必须识别状态与留痕记录不一致并停止。
5. 东方农博2024年回溯中的16个业务组成不得再仅凭“无效输入”或“小金额批次处理”被排除；其中具体现金流项目仍应依据各自摘要、完整路径和人工证据判断，不得为了勾稽一致统一强塞同一个项目。

## 九、真实付款不得与同凭证非现金计提错误合并

### 9.1 已确认根因

1. 2025年8月8日记-26同时包含185,674.66元实际发放工资、2,134.77元个人所得税结转和200.00元补计提工资。
2. 现行业务组成程序沿“应付职工薪酬”把实际工资付款、个人所得税结转和补计提工资连接成同一个业务组成，没有先剥离金额自行抵平的非现金附带分录。
3. 组成内同时出现“发放7月工资”和“补计提7月工资”后，程序将业务组成摘要清空并标记为“同凭证摘要分配存在多种合理组合”。随后非法输入处理又把本来能够独立识别的完整科目路径一并清为0分，最终错误转入重要待复核事项。
4. 摘要“发放7月工资”能够独立形成“支付给职工以及为职工支付的现金”候选，质量为中等、25分；完整路径“应付职工薪酬_工资”能够独立形成同一候选，质量为强、45分。正确业务组成下两项来源合计70分、候选唯一，不应转人工。
5. 现有非现金检查只在整张凭证的全部摘要均包含“计提”时生效，无法处理“真实现金付款与非现金计提混在同一凭证”的情况。
6. 本次运行中至少有4笔工资业务受到同类错误影响，合计684,796.05元：2025年8月8日185,674.66元、2025年9月10日178,722.24元、2025年10月10日174,359.64元、2025年11月10日146,039.51元。

### 9.2 修复要求

1. 业务组成必须先围绕真实现金腿识别与现金金额唯一闭合的对方分录，不得仅因同凭证科目能够连通就把全部非现金分录并入现金业务。
2. 单一现金腿具有明确摘要时，应检查同摘要对方分录及其金额关系；存在唯一、最精简且金额与现金腿闭合的组合时，以该组合作为现金业务组成。
3. 同凭证内借贷自行抵平的个人所得税结转、工资补计提、费用计提及其他非现金附带分录，不得污染真实现金业务的摘要、完整路径、候选和分数。
4. 若金额闭合存在多个同样合理的最小组合，继续生成业务组成确认请求，不得猜测；本修复不得降低原有结构确认门禁。
5. 一个来源因真实输入缺失而无效时，不得无条件删除另一项本来有效的独立来源；尤其不得把程序自身错误清空的组成摘要进一步扩散为完整路径0分。
6. 正确拆分后，工资现金付款应使用实际付款摘要和实际现金对应路径重新执行摘要、路径、评分和行动路由，不为工资业务编写客户专属特例。

### 9.3 验收条件

1. “发放工资＋个人所得税结转＋补计提工资”位于同一凭证时，实际工资付款必须形成“支付给职工以及为职工支付的现金”唯一候选，非现金附带分录不得进入该现金组成的完整路径。
2. 2025年8月8日记-26的摘要来源应为25分、完整路径来源应为45分、合计70分，不得再显示两项来源均为0分或进入人工决定。
3. 本次已识别的4笔同类工资业务必须全部重新核对，不得仅修复单一凭证。
4. 测试必须覆盖单一现金腿、多条同摘要分录、净额自行抵平的非现金附带分录、不同摘要的计提分录，以及存在多个金额闭合组合的真正歧义场景。
5. 修复后必须重新统计重要待复核事项数量、尚待分类现金净额和最终勾稽状态，并验证现金金额未丢失、未重复、未因拆分发生变化。

## 十、人工处理表只展示真实明细，不生成“批次主行”

### 10.1 已确认根因

1. 现行“重要待复核事项”在真实现金分配明细之外，额外为每个业务组成生成一条程序构造的“批次判断”汇总行。该行不是原始序时账或现金明细中的真实记录。
2. 为避免再次把多个借方、贷方或流量金额拼入一个单元格，输出程序将批次判断行中不能保持单一数值的字段直接清空。该处理只消除了拼接形式，没有提供合计或明确说明，导致使用者看到无原因的空白。
3. 真实现金分配明细的人工确认项目由公式引用上述汇总行，程序又在明细行写入“明细随批次主行生效”。该文字是内部实现说明，不是会计事实或人工处理结果。
4. “重要待复核事项”中的多行只是同一业务对应的多条真实现金分配明细，不属于多个业务组成的处理批次。输出程序错误复用了“低金额人工批量”的批次结构和称呼。

### 10.2 修复要求

1. “重要待复核事项”不得再生成任何脱离原始资料的批次判断行、汇总控制行或其他人造数据行，只展示真实现金分配明细。
2. 同一业务的全部真实明细必须连续排列，并使用清晰、稳定的“同一业务序号”识别归组；每条明细保持一行一个真实金额。
3. 同一业务只需作一次人工判断：第一条真实明细提供人工确认下拉，所属后续真实明细通过公式同步该结果，并直接显示具体现金流量表项目名称。
4. 后续明细不得留空人工确认项目，也不得显示“明细随批次主行生效”“采用主行结果”等程序内部文字。
5. 日期、凭证号、摘要、完整路径、现金账户、借方、贷方、本行现金变化、系统候选、证据状态和异常等真实字段逐行展示；同一业务的公共事实可以重复显示，不得为了去重造成无含义空白。
6. 从人工处理表删除“行类型”“批次最不利影响金额”“批次现金变化金额”“人工处理状态”和以长文本列示全部选项的“人工可选标准项目”。可选项目只通过Excel下拉提供。
7. 人工下拉必须按现金方向限制：现金流入只提供流入项目，现金流出只提供流出项目；最终公式或校验再执行一次方向门禁，方向相反的选择不得生效。
8. “低金额系统兜底明细”不得使用低金额批次编号，也不得生成虚构汇总数据行；只以“同一业务序号”标识真实属于同一业务的明细。第一条真实明细承担一次改选，其余真实明细同步显示具体项目。

### 10.3 验收条件

1. 人工处理表的数据行数量必须等于实际输出的真实现金分配明细数量，不再额外增加一条业务组成汇总行。
2. 同一业务存在多条现金明细时，每条明细金额均为单一数值，合计等于该业务现金变化；不得出现拼接金额、重复计量或人造合计行。
3. 同一业务首条真实明细改选项目后，所属全部真实明细和正表公式同步更新，并在每条明细中显示同一个具体项目名称。
4. 工作簿全局不得出现“批次主行”“明细随批次主行生效”或含义相同的内部实现文字。
5. 现金流出不得选择任何现金流入项目，现金流入不得选择任何现金流出项目；下拉列表和最终校验均须覆盖该要求。
6. 本次东方农博运行重新生成后，当前38条人造判断行必须消失；真实明细按修复后的业务组成重新统计和展示。

## 十一、低金额系统兜底结果必须单独展示并允许人工改选

### 11.1 适用范围和工作表定位

1. 最终工作簿用独立工作表“低金额系统兜底明细”直接替换原方案中的“低金额批量处理”，两张表不得并存。
2. 低于本次实际执行重要性的适用事项全部由系统兜底形成具体现金流量表项目，不再保留“低金额人工批量”行动结果或工作表。
3. 系统兜底结果属于当前有效默认结果，不再计入尚待分类现金净额；但必须完整展示，供人工抽查和主动改选，不得因已经兜底而从人工可见底稿中隐藏。
4. 本次东方农博运行中已识别的683笔系统兜底事项应进入该工作表；重新运行后以修复后的实际数量为准，不硬编码683。

### 11.2 展示要求

1. 工作表只展示真实现金分配明细，不生成批次主行、业务汇总行或其他人造数据行。
2. 每条明细至少展示：同一业务序号、日期、凭证号、摘要、完整对方科目路径、现金账户、现金方向、本行金额、原项目状态、摘要来源候选及分数、完整路径来源候选及分数、系统兜底项目、兜底采用来源、兜底步骤、兜底原因、人工改选项目和最终采用项目。
3. 同一业务存在多条真实现金分配明细时连续展示；第一条真实明细提供一次人工改选入口，其他明细同步显示同一具体结果。
4. 默认状态直接采用系统兜底项目，不要求人工逐条确认；人工不操作时，系统兜底项目继续有效。
5. 不得使用“等待人工”“批次主行”“明细随批次主行生效”等文字描述已经形成默认项目的系统兜底事项。

### 11.3 人工主动改选和正表联动

1. “人工改选项目”必须提供Excel下拉。第一项为“采用系统兜底项目”，其余只允许选择与本行现金方向相容的具体正表项目。
2. 现金流入不得选择现金流出项目，现金流出不得选择现金流入项目；下拉列表和最终公式必须各自执行一次方向校验。
3. 人工选择其他项目后，最终采用项目立即改为人工选择，并通过公式从原系统兜底项目转出、转入人工选择项目。
4. 人工改选必须直接联动“现金流量表正表”“正表核对报告”“现金范围与现金流量表与货币资金变动的勾稽核对”和“全量分类留痕”，无需重新运行程序或把选择导回运行状态。
5. 改选只能改变项目归属，不能改变本行现金金额、现金方向和现金变动总额；改选前后现金变动桥接必须保持守恒。
6. 人工未改选时不形成未决事项；人工改选为合法具体项目后同样不形成未决事项。方向不相容、空白以外的非法值或公式失效时，工作簿必须提示错误并阻止标记“最终可使用”。

### 11.4 验收条件

1. 本次运行的系统兜底事项全部能够在“低金额系统兜底明细”逐笔追溯，数量和金额与运行状态中的兜底决定一致。
2. 随机抽取不同兜底来源、不同现金方向和不同金额档位的明细，核对系统兜底项目、兜底原因和两项独立来源均与留痕一致。
3. 对一笔系统兜底现金流入和一笔系统兜底现金流出分别改选为同方向其他项目，正表项目间转入转出准确，现金净增加额和桥接差异保持不变。
4. 尝试为现金流出选择现金流入项目、为现金流入选择现金流出项目时，必须无法通过下拉选择；人为写入非法值时，最终校验必须报错。
5. 人工不操作任何兜底明细时，正表继续使用全部系统兜底结果，不得因新增抽查工作表重新产生尚待分类现金净额。

## 十二、冒烟测试必须作为全新运行重新取数

1. 开始冒烟测试前必须暂停并询问用户，由用户重新提供本次测试文件路径和全部运行参数。
2. 用户尚未重新提供完整输入前，不得启动冒烟测试，也不得从东方农博本轮运行、历史运行记录、缓存、默认配置或此前对话中沿用任何设置。
3. 必须重新确认的输入至少包括：序时账文件路径、拟使用的工作表、现金范围及排除账户、整体重要性、实际执行重要性、明显微小错报临界值、期初现金及现金等价物余额、外币汇率影响和公司特殊核算规则；如程序还有其他必填参数，也必须一并重新询问。
4. 本门禁只针对冒烟测试输入。代码层自动化测试可以使用专门构造的测试数据，但不得把历史客户数据或历史客户参数伪装成用户重新确认的冒烟测试输入。
5. 验收记录必须保留用户本次重新提供的文件路径、参数确认结果和测试时间，能够证明该冒烟测试确实从头开始，而非复用旧运行。

## 十三、本轮建立完整的统一规则中心

### 13.1 本轮实施顺序

1. 本轮先完成并验证前述已确认问题，确保当前修复本身有独立、清晰的测试结果。
2. 当前修复通过自动测试后，再建立完整的统一规则中心并迁移现有规则，不把两部分改动混成一次无法定位原因的大改。
3. 规则迁移完成后重新执行全套自动测试；不得用规则中心改造前的测试结果代替迁移后的验证。
4. 两部分均通过后，才进入第十二节规定的全新冒烟测试取数门禁。

### 13.2 集中管理的范围

统一规则中心至少分门别类管理以下内容：

1. 一般企业现金流量表正表项目及现金流入、流出方向。
2. 完整科目路径语义及其候选项目。
3. 摘要文字语义及其候选项目。
4. 两项独立来源的证据质量、分数和合并规则。
5. 原项目状态、重要性层级、证据状态与处理动作之间的行动规则。
6. 一次人工智能复核、互盲复核、追加复核及失败后的最终出口。
7. 空白原项目低金额系统兜底规则，包括较高分来源优先、同分路径优先和无法形成唯一候选时的最终兜底顺序。
8. 工资、个人所得税、增值税伴随项目、内部划转、现金范围、净额列报、非现金事项和受控排除等特殊业务规则。
9. 未决现金、确认调整、现金变动桥接、最终勾稽和可用状态规则。
10. 人工事项、低金额系统兜底明细、下拉改选、正表联动及工作簿输出规范。

### 13.3 统一入口和边界

1. “统一规则中心”不是把全部规则塞进一个巨大文件，而是按上述类别分别保存，由一个统一入口负责加载、校验、提供调用和记录版本。
2. 各业务模块不得自行复制评分档位、重要性动作、人工智能失败出口、兜底顺序、人工事项范围或废止动作；只能调用统一入口取得结果。
3. 程序代码仍负责读取数据、形成业务组成、计算金额、执行公式和生成工作簿等处理过程；会计判断条件、动作选择、优先顺序和输出口径应由规则中心统一提供。
4. 公司特殊核算规则和现金范围仍属于每次运行由用户确认的输入，不得写入通用规则中心；规则中心只管理如何验证、采用和留痕这些本次输入。
5. 重要性金额必须读取本次运行参数；规则中心只保存“低于实际执行重要性”“达到实际执行重要性”等相对条件，不得写死具体金额。

### 13.4 每条规则的最低登记内容

每条能够影响分类、评分、行动、勾稽或最终输出的规则至少应登记：规则编号、中文名称、所属类别、适用条件、不适用条件、处理结果、优先顺序、制定理由、启用状态、生效版本和对应测试。涉及候选项目的，还应登记证据来源、分数及现金方向；涉及废止或替代的，还应登记替代规则。

### 13.5 废止动作清理

1. “低金额人工批量”在本轮属于正式废止动作，必须从首次行动判断、人工智能复核结束出口、重要性处理、人工队列、最终校验、留痕、工作簿和现行文档中全部清除。
2. 旧运行记录如包含该动作，只能明确提示规则版本失效并要求重新运行，不得继续按旧动作生成最终工作簿。
3. 自动检查必须扫描现行程序和当前文档，阻止废止动作重新出现；历史需求、历史评审记录可以保留原文，但不得被当前程序加载或被现行说明引用为有效规则。

### 13.6 版本、追溯和验收

1. 统一入口必须校验全部现行规则文件的结构、相互引用、现金方向、项目编号、动作名称和优先级冲突。
2. 所有现行规则必须纳入统一版本指纹；任一规则变化后，依赖旧规则的运行状态必须失效并要求重新运行。
3. 每笔分类结果和处理动作必须能够追溯到具体规则编号及规则版本，不得只显示无法定位来源的自由文字理由。
4. 迁移前先用当前修复后的测试固定正确结果；迁移后同一批测试结果必须保持一致，除非差异正是本需求明确要求的改变。
5. 测试至少覆盖：规则文件缺失、重复编号、无效项目、方向冲突、重复优先级、废止动作残留、版本变化、同一条件多项互斥结果和完整调用追溯。
6. 规则中心迁移后必须重新运行全部自动测试、技能结构检查、程序编译检查和文档一致性检查，全部通过后才能向用户申请冒烟测试输入。
